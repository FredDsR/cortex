# tracking-work-sync — design

**Date:** 2026-04-23
**Status:** Draft (awaiting implementation)
**Scope:** Optional sub-skill that syncs `~/.work/` (the global `tracking-work` store) across devices using git + a private GitHub repo.

## Goals

- Sync session state (SUMMARY + tasks + archive) across multiple devices.
- Support concurrent editing across devices — two machines may write near-simultaneously.
- Zero-friction bootstrap on a new device: clone-or-create-or-skip, one interactive setup.
- Fully opt-in. If sync is not enabled, the main `tracking-work` skill behaves exactly as today.
- No background daemons, no periodic cron jobs. Sync fires only at checkpoints driven by the main skill.

## Non-goals

- Auto-merging concurrent edits to the same task file.
- Per-workspace isolated repos (everything under `~/.work/` syncs as one repo).
- Encryption at rest beyond what GitHub private repos provide.
- Mobile / iOS clients.
- Syncing device-local state (`.active.*`, `.meta`).

## Architecture

A new sub-skill lives at `~/.claude/skills/tracking-work-sync/`, following the pattern of `tracking-work-github` and `tracking-work-migration`. The main `tracking-work` skill invokes it at defined checkpoints; if sync is not enabled the invocations are no-ops.

Trust boundary: a single private GitHub repo owned by the user holds the history of `~/.work/`. Authentication is delegated to `gh` CLI (already used by the `tracking-work-github` sub-skill).

## Repo shape

`~/.work/` *is* the git working tree. The top-level `.gitignore` is:

```
.active.*
.meta
```

Rationale:

- `.active.<session-id>` is per-agent/per-shell. Filenames already include a device/agent-unique ID, so technically they could sync, but they have no cross-device meaning and their sweep/deletion semantics are local — so exclude them.
- `.meta` contains a `cwd:` field pointing to a local filesystem path that differs between devices. Must stay local. A fresh `.meta` is rebuilt on each device when slug resolution runs.

Everything else under `~/.work/` — `workspaces/<slug>/sessions/...`, `archive/` — is tracked.

## State detection

At the start of any main-skill invocation the sub-skill exposes `is_enabled.sh`:

- Exit 0 (sync enabled): `~/.work/` is a git repo *and* has a remote `origin` configured.
- Exit 1 (sync disabled): anything else, or `~/.work/.sync-disabled` sentinel present.

This gives three unambiguous states: active, off-by-choice (sentinel), and unconfigured (no repo or no remote and no sentinel).

## Bootstrap — the three paths

When the main skill starts on a device and detects the "unconfigured" state, it delegates once to `setup.sh`, which prompts with three options:

### 1. Clone an existing sync repo

For a second (third, Nth) device.

- User provides `<owner>/<repo>` or a full URL.
- Script refuses if `~/.work/` already contains any tracked content (refuses to overwrite existing local sessions silently).
- If `~/.work/` is empty or absent: `git clone <url> ~/.work`.
- Verifies `gh auth status` first; if not authenticated, prompts the user to run `gh auth login` and exits cleanly.

### 2. Create a new sync repo

For the first device.

- Verifies `gh auth status`; on failure, prompts the user to run `gh auth login` and exits cleanly.
- `git init ~/.work` (if not already a repo).
- Write the `.gitignore` from `templates/gitignore`.
- Stage any existing content and commit as `track: initial sync state`.
- `gh repo create <name> --private --source ~/.work --push`. Default name: `work-tracking`, overridable by user prompt.
- Remote `origin` is now set; `is_enabled.sh` will return 0 from this point.

### 3. Skip sync (local only)

- Touch `~/.work/.sync-disabled` (the sentinel).
- No git init, no remote. Main skill continues as today.
- The sentinel makes this choice sticky — future session starts won't re-prompt on this device.

The setup UX is intentionally a single prompt with three numbered options plus any necessary follow-ups (repo URL, repo name). Target: under 30 seconds for any path.

## Sync checkpoints

The main skill's checkpoint rules table gains the following sync actions (each a no-op if `is_enabled.sh` returns 1):

| Trigger | Sync action |
|---|---|
| Session start (after `sweep_active.sh`) | `pull.sh` |
| Any write to `tasks/<slug>.md` or `SUMMARY.md` | `commit_push.sh "<message>"` |
| Session close (after archive move) | `commit_push.sh "track: archive session <slug>"` |

Commit message convention: `track: <verb> <session>/<task>` — e.g. `track: open task fix-auth in refactor-api`, `track: update summary for refactor-api`, `track: archive session refactor-api`. Keeps log readable and greppable.

### Why push-on-every-write, not batched

For the concurrent-multi-device target case, pushing immediately keeps Device B's view fresh when B starts its next session. Batching to session-close would leave B pulling stale state and increase the probability of task-file conflicts. Commit noise is a cheap cost to pay; stale state has a real cost (lost work during merges).

## Conflict handling

Only two file types can conflict under `git pull --rebase`:

### `SUMMARY.md`

Auto-resolved. The main skill already treats SUMMARY as derived from task files ("regenerate, don't hand-edit"). On conflict, `pull.sh` accepts the upstream version of SUMMARY.md (using whichever of `git checkout --ours`/`--theirs` matches the upstream side during rebase — `--ours` during `rebase`, `--theirs` during `merge`), continues the rebase, and emits a signal that the main skill should regenerate SUMMARY.md from the now-merged task files at the next checkpoint. No user involvement.

### `tasks/<slug>.md`

Surfaced. On a rebase conflict in a task file, `pull.sh` aborts cleanly with a structured message naming the conflicting session/task and showing the three-way diff. The main skill presents this to the user and lets them resolve manually. No auto-merge attempted — silent Status field merges would be dangerous.

In practice, because only the agent writes and every write is pull-before-commit, the window for a same-task conflict is on the order of the sync round-trip time (seconds). Expected frequency: rare.

## Sub-skill file layout

```
~/.claude/skills/tracking-work-sync/
├── SKILL.md                 # when to use, invocation rules, state machine
├── scripts/
│   ├── setup.sh             # interactive bootstrap (clone / init / skip)
│   ├── is_enabled.sh        # exit 0 if sync active
│   ├── pull.sh              # pull --rebase + auto-resolve SUMMARY, surface task conflicts
│   └── commit_push.sh       # stage, commit <msg>, push; no-op if disabled
├── templates/
│   └── gitignore            # .gitignore content for ~/.work/
└── docs/
    └── 2026-04-23-design.md # this document
```

### Script contracts

- `setup.sh` — interactive; returns 0 on successful configuration (any of the three paths), non-zero on abort. Safe to re-run; detects current state and offers only relevant paths.
- `is_enabled.sh` — silent, fast (`git -C ~/.work remote get-url origin` + sentinel check). Used everywhere as a gate.
- `pull.sh` — calls `is_enabled.sh`; on enabled, runs `git pull --rebase`. Handles SUMMARY conflicts automatically. On task conflicts, aborts rebase and prints a structured report. Exit codes: 0 clean, 2 task-file conflict surfaced, other non-zero for unexpected errors.
- `commit_push.sh "<message>"` — calls `is_enabled.sh`; stages `~/.work/` (respecting `.gitignore`), commits with the given message (skips if nothing to commit), pushes. Idempotent.

## Changes to the main `tracking-work` skill

Three edits to `~/.claude/skills/tracking-work/SKILL.md`:

1. **Session Start Flow** — after the existing sweep, add: "Run `$HOME/.claude/skills/tracking-work-sync/scripts/pull.sh` (no-op if sync not enabled). If it exits 2, surface the reported conflict to the user and stop."
2. **Bootstrap detection** — if `~/.work/` is missing, unconfigured, and has no `.sync-disabled` sentinel, invoke `setup.sh` once before proceeding.
3. **Checkpoint Rules table** — add the three sync rows from the table above.

No other script in the main skill changes. `resolve_workspace.sh`, `resolve_session_id.sh`, `sweep_active.sh`, `list_sessions.sh` all continue untouched.

## Failure modes and recovery

- **Network offline at session start** — `pull.sh` fails; surface a warning and proceed in local-only mode for this session. Next successful checkpoint will push accumulated commits.
- **`gh` not installed or not authenticated** — `setup.sh` detects and exits with a clear remediation message. No partial state left behind.
- **Remote diverged beyond auto-resolvable** — `pull.sh` exits 2 with a task-conflict report. User runs normal `git` commands in `~/.work/` to resolve; no special tooling needed.
- **User blows away `~/.work/` on a device** — next session start hits the bootstrap flow; they pick "clone" to restore.

## YAGNI / explicitly deferred

- Encryption at rest (git-crypt, age) — revisit only if a user stores secrets in task notes.
- A `--dry-run` mode for setup.
- Multi-remote support (mirroring to a second provider).
- A `tracking-work-sync status` command — `git status` in `~/.work/` already works.
